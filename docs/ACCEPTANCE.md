# Проверка критериев ТЗ

Основание — PDF «вся инфа о кейсе», 19 страниц, разделы постановки задачи, критериев успеха и ограничений. Демка из исходной папки Drive не использовалась. Визуальная основа взята только из отдельно предоставленного пользователем `alfa-pulse.zip`.

ТЗ не задает HTTP-ручки, отдельную регистрацию или банковский endpoint авторизации. Эти решения согласованы в чате. Текущий продукт — автономный прототип в оформлении Альфа-Бизнеса; реальная интеграция с банковским identity provider не заявляется.

| Критерий | Реализация и проверка | Граница результата |
|---|---|---|
| 01. Контекст клиента и значимость событий | Признаки компании/группы, CSV, связи, роль, настройки; тест смены компании и роли | Доля рынка не выдумывается. Распознавание отраслей основано на расширяемом словаре |
| 02. Экспертиза Альфа-Банка влияет на выводы | Отдельные материалы `bank_analytics`, блок позиции банка и передача этих материалов в интерпретацию; тест нового банковского материала | Нужны оригинальные отчеты из кейса. В поставке их нет; синтетические оценки банка удалены |
| 03. Отбор, объединение и связь с источниками | Парсер RSS/text/PDF, хеши версий, дедупликация, цитаты и ID признаков, проверка ссылок | Структурная проверка не доказывает смысловую истинность выводов; требуется экспертная оценка |
| 04. Работа на ранее не показанных новостях | Нет списка жестко зашитых production-событий; новые материалы проходят общий конвейер; тест импорта нового материала | Устойчивость качества на реальных новостях должна проверяться с разрешенной LLM и реальными источниками |
| 05. Полный сценарий от входа до интерпретации | Регистрация, вход, выбор компании/роли, сводка, разбор, источники, вопрос, оценка, история; HTTP E2E и браузерная проверка | Без ключа LLM произвольный вопрос честно возвращает нехватку подключения |
| 06. Содержательная персональная интерпретация | В LLM передаются снимок признаков, событие, банковская аналитика, роль; модель формирует причинные сценарии | Качество нельзя подтвердить без провайдерского endpoint. Режим правил ограничен и помечен отдельно |
| 07. Масштабирование и сопровождение | Порты, адаптеры, SQLAlchemy, миграции, worker, Docker, конфигурация источников | Для больших наборов нужны keyset-пагинация, более точный поиск/RAG, политика очистки и нагрузочное тестирование |
| 08. Постоянная точка входа | Раздел «Обзор» и «Все события» в сохраненном интерфейсе Альфа-Бизнеса | Это оболочка прототипа; в реальный интернет-банк код не встраивался |
| 09. Вопрос, иной разрез, первоисточник | Контекстный чат, `perspective`, `parentAnswerId`, ссылки и выдержки | Полноценная генерация зависит от настройки модели; источники без разрешенной ссылки показаны как недоступные извне |
| 10. Агентная логика | План → контекст → поиск → классификация → ранжирование → интерпретация → проверка → повтор при ошибке; тест адаптации | Оркестрация своя. Перепоиск по открытому интернету, неограниченные инструменты и внешние готовые агенты отсутствуют |
| 11. Трассируемость | Записи этапов, источники, признаки, версии, requestId; вкладка реальной серверной трассы | Скрытые рассуждения не выводятся; семантическую полноту промежуточных результатов должен оценить эксперт |
| 12. Мониторинг качества | Оценки пользователей, ошибки задач, длительность, покрытие банковской аналитикой, отчет `python -m app.quality` | Процесс экспертной разметки и целевые пороги предложены ниже; регулярный production-мониторинг не выполнялся |

## Ограничения и безопасность

- Только разрешенное семейство модели, провайдерский ID из конфигурационного allowlist; дневной резерв стоимости не более 500 RUB.
- Пароль Argon2, короткий JWT, ротация refresh, отзыв сессии, rate limit входа, изоляция пользователей и компаний. Тесты проверяют повторное использование refresh и чужие сводки.
- Источники только из операторской конфигурации, HTTPS, без редиректов на произвольные адреса. Нужен дополнительный сетевой egress allowlist для production.
- Неполные данные отмечаются явно. Финансовый эффект, доля рынка и экспертная позиция не подменяются выдуманными числами.
- Автоматических действий с банковскими продуктами и платежами нет. Предложения являются направлениями проверки.

## Комплект сдачи

Есть история отдельных Git-коммитов, README, Dockerfiles и два Compose-проекта, `uv.lock`, пустое дерево npm-зависимостей с lock-файлом, синтетические тестовые данные, OpenAPI, тесты, deploy-файлы и THIRD_PARTY_NOTICES. Версию для сдачи нужно зафиксировать `git rev-parse HEAD` после выбора окончательного коммита. Дедлайн и доступ судей к приватному репозиторию в этой задаче не предоставлены; эти действия не выполнялись.

## Предлагаемый процесс оценки качества

На каждом изменении: merge checks с PostgreSQL, проверка контракта, изоляции, импорта и двух Compose-проектов. На обновлении модели/промпта: не менее 20 ранее не использованных новостей по нескольким компаниям, ручная оценка релевантности, точности фактов, причинной связи, корректности позиции банка и достаточности цитат. Ошибка факта или ложное приписывание банку блокирует выпуск.

Собирать полезность последних оценок, причины отказов, долю ответов без данных, долю неподтвержденных источников, latency p95 и ошибочность задач. Отчет оператора:

```sh
docker compose -f backend/compose.yaml exec api python -m app.quality
```

Отчет агрегирован и не выводит персональные данные или тексты пользовательских вопросов. Конкретные целевые пороги нужно установить по реальному тестовому набору; выдуманные результаты качества здесь не приводятся.
