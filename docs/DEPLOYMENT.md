# Развертывание

## Два Compose-проекта на одном сервере

Минимум: Linux с Docker Engine и Compose v2.24+, 2 CPU и 2 ГБ RAM для прототипа. Модель вызывается через внешний разрешенный HTTP endpoint; веса LLM на сервер не загружаются.

```sh
docker compose -f backend/compose.yaml up -d
docker compose -f frontend/compose.yaml up -d
```

Backend: PostgreSQL → одноразовая миграция → API → worker. Frontend: nginx с прокси `/api/v1`. Общая сеть `alfa-pulse-edge` создается первым проектом и используется вторым. БД не публикует порт на хост. API доступен только через `127.0.0.1:8000`, frontend — `127.0.0.1:8080`. Межсерверное развертывание потребует другого upstream и сетевого туннеля; текущие файлы рассчитаны на один Docker-хост.

По умолчанию сеть PostgreSQL внутренняя, worker имеет отдельную сеть для исходящих HTTPS-запросов к источникам и LLM. API подключен к общей сети frontend. Контейнеры приложения работают без root и дополнительных capabilities.

## Настройка перед публичным размещением

Скопируйте `.env.example` в `.env` внутри backend и frontend. Задайте свои пароли, секрет JWT, `DEMO_DATA=false` и параметры оператора. Не коммитьте `.env`. `POSTGRES_PASSWORD` после создания тома не меняет пароль уже созданной роли: для ротации нужна операция внутри PostgreSQL, а затем обновление конфигурации.

Если синтетические данные уже были загружены, `DEMO_DATA=false` предотвращает новые выдачи доступа к ним, но не удаляет ранее созданные записи. Для реальных данных используйте отдельное чистое окружение/том с заранее настроенным `DEMO_DATA=false`.

Снаружи публикуется только HTTPS reverse proxy. Пример Caddy-конфигурации: `deploy/Caddyfile.example`. Запускайте Caddy на том же сервере перед `127.0.0.1:8080`. Настройте DNS своего домена и TLS, не открывая PostgreSQL или служебный API-порт. Пример не загружает сертификаты и не меняет DNS автоматически.

Для HTTP-тестирования с другой машины можно задать `WEB_BIND=0.0.0.0`, но перед передачей настоящих паролей нужен HTTPS. Запуск из каталога компонента гарантирует чтение его `.env`:

```sh
cd backend
docker compose up -d --build
cd ../frontend
docker compose up -d --build
```

## Обновление и откат

`deploy/update.sh` получает текущую ветку fast-forward, собирает образы и обновляет проекты в правильном порядке. Перед обновлением сделайте резервную копию. Для отката выберите проверенный commit/tag, пересоберите образы. Миграции данных могут быть несовместимы со старым кодом, поэтому автоматический откат БД не выполняется.

```sh
sh deploy/backup.sh
sh deploy/update.sh
```

Копия создается в `backups/` с правами только владельца. Каталог исключен из Git. Проверять восстановление следует на отдельной тестовой базе. Остановка обычным `docker compose down` не удаляет том PostgreSQL; вариант `down -v` удаляет данные и для рабочего окружения не используется.

## Диагностика

```sh
docker compose -f backend/compose.yaml ps
docker compose -f backend/compose.yaml logs --tail 100 api worker migrate
docker compose -f frontend/compose.yaml logs --tail 100 web
curl --fail http://127.0.0.1:8000/healthz
```

Ошибка 502 на фронте обычно означает, что backend еще не готов или проекты не используют общую сеть. `queued` без прогресса — проверьте worker. После аварии worker задача `running` может ждать до десяти минут до повторного захвата; результат записывается под заранее выделенным ID. Вызов LLM может повториться, если процесс завершился после ответа провайдера и до сохранения результата, поэтому бюджет резервируется перед каждым вызовом.

Нужны внешние политики хранения и резервного копирования. Сейчас сессии/refresh, оценки и снимки автоматически по времени не удаляются. Для больших объемов потребуются очистка истекших данных, keyset-пагинация и специализация таблиц JSONB. Долгие PDF/CSV и ограничения ресурсов следует вынести в отдельные очереди и подобрать по нагрузочным тестам.
